# 프로덕션 안정화 및 후속 개선 투두 — 2026-09-27

## 목적과 현재 상태

기능 추가보다 권한 통제, 데이터 복구, 콘텐츠 일관성, 배포 복구를 먼저 확보한다. 그다음 측정한 병목을 줄여 성능과 운영 비용을 개선한다.

- 계획 작성 이후 A1 백업·복구와 A2 인증 구현·검증을 완료했다. 다른 계정·만료 세션은 인증 핸들러 런타임에서 확인했으며, Cloudflare 원격 D1을 이용한 같은 검증은 현재 권한 오류로 보류 중이다.
- 기존 구현에 있는 본인 계정 검사, Markdown 정제, SQL bind, revision/중복 요청 방어, 이미지 참조 확인은 유지한다. 같은 기능을 새로 만드는 작업으로 잡지 않는다.
- 분석에서 실제 계정 침해나 토큰 탈취를 확인한 것은 아니다. 일부 코드상의 위험과 운영 응답을 확인했으며, 전체 보안·복구·성능을 보증한 상태는 아니다.
- 현재 청구액, 계정 플랜, D1/R2 실제 크기, endpoint별 CPU·DB 읽기량은 아직 확인하지 않았다.
- 실행 순서는 이 문서를 기준으로 한다. 기존 분석 문서의 항목별 우선순위는 근거로 보존한다.
- 과거 글쓰기 의사 결정 문서는 당시 Git/Decap 방식의 역사 기록이다. 현재 D1 방식의 실행 계획으로 사용하지 않는다.
- 2026-09-28에 D1 상세 페이지에서 기존 시리즈 전체 글 페이지네이션이 누락된 회귀를 확인했다. A3의 첫 작업으로 복원한다.

## 확정한 방향

1. Astro + 사이트/CMS Workers + D1 + R2 + GitHub Actions를 유지한다.
2. 첫 실행은 실제 운영 데이터의 백업·복구 확보다. 가장 먼저 바꿀 주요 코드 영역은 인증이다.
3. D1을 운영 콘텐츠의 기준으로 삼고 레거시 Git 편집·정적 검색 fallback을 정리한다.
4. GitHub는 본인 확인에 필요한 최소 권한으로 사용한다. 브라우저에 GitHub access token을 전달하지 않는다.
5. 서버에서 폐기 가능한 자체 세션으로 관리 기능을 인증한다.
6. 이미지 자동 정리의 7일 유예, 삭제 직전 최신 참조 확인, 확인 실패 시 삭제 중단을 유지한다.
7. 공개 캐시는 발행·수정·삭제·복원에 대한 무효화 설계와 함께 적용한다.
8. 저장소 private 전환과 유료 플랜 전환은 아직 확정하지 않는다. 영향과 실제 사용량을 확인한 뒤 결정한다.
9. 새로운 DB, Redis, Queue, 외부 모니터링 구독을 먼저 추가하지 않는다. 기존 기능과 플랫폼 수단을 우선 활용한다.

## A. 먼저 끝낼 안정화 작업

아래 A1–A4가 첫 안정화 범위다. 시리즈 목록 복원은 기존 기능의 회귀 수정으로 A3에 포함한다. 새 기능 요청과 후속 최적화는 별도 목록에 둔다. 각 단계에서 필요한 검증과 기록까지 끝낸 뒤 다음 단계로 이동한다.

### A1. 운영 백업과 복구 확보

근거: 장기 운영 문서의 데이터 보호 계획. SQL만으로 삭제된 R2 이미지는 복구할 수 없다.

- [x] 현재 운영 D1의 실제 SQL 백업을 확보한다. Git에서 초기 적재 파일을 만드는 도구와 구분한다.
- [x] 글·초안·시리즈와 이미지 참조가 백업에 포함되는지 확인한다.
- [x] 이미지 복구 기간을 정하고, 필요한 R2 사본과 보관 위치를 확보한다. 7일 미사용 삭제 유예와 백업 보관 기간은 별개로 관리한다. 주간 최근 4회·월간 최근 12개 정책을 도구에 기록하고 자동 실행을 확인했다.
- [x] SQL·초안·세션 정보가 공개 버킷이나 공개 저장소에 노출되지 않게 보관한다. 복구된 세션은 활성화하지 않는다.
- [x] 운영 DB를 덮어쓰지 않는 별도 환경에서 글·초안·시리즈 및 대표 이미지를 복구한다.
- [x] 백업 생성·복구 명령, 보관 위치, 실패 대응을 실행 문서로 기록한다. 비밀값은 기록하지 않는다.
- [x] 주간 최근 4회·월간 최근 12개 독립 SQL·이미지 암호화 사본 보관을 확정하고, 기존 GitHub Actions/R2로 자동화했다.

**완료 조건:** 실제 운영 백업으로 별도 환경의 콘텐츠와 대표 이미지를 복구한 근거가 있다. 복구 가능한 기간과 이미지 복구의 한계를 문서에서 알 수 있다.

### A2. 인증과 세션 통일

근거: 보안 S01/S02/S04, 성능의 반복 GitHub 인증 조회.

- [x] 같은 origin의 로그인·콜백·관리 API 흐름을 정리하고 host-only HttpOnly 세션으로 통일한다. 가능한 경우 `__Host-` 쿠키 조건을 적용한다.
- [x] 무작위 세션 ID와 서버 레코드로 만료·폐기를 처리한다. 원본 세션 ID를 로그에 남기지 않는다.
- [x] 본인 계정 검사, OAuth state, 정확한 메시지 origin/source 검사와 변경 요청 Origin/CSRF 방어를 유지한다.
- [x] GitHub 토큰의 팝업 전달과 sessionStorage 보관을 없앤다.
- [x] 관리 API의 별도 GitHub Bearer 인증 경로와 광범위한 Domain 쿠키를 제거한다.
- [x] OAuth의 요청 scope를 `read:user`로 축소했다. 남아 있는 Git 편집 코드는 D1 모드에서 사용되지 않으며 A3와 함께 제거한다.
- [x] 로그아웃 시 서버 세션을 폐기한다. 로그아웃 뒤 편집 API 세션 확인이 401을 반환하는 것을 확인했다.
- [x] 기존 넓은 권한 토큰 폐기와 `read:user` 재동의를 완료했다.
- [x] 비로그인 상태의 세션·관리 API 거부를 확인했다.
- [x] 다른 계정과 만료 세션을 거부하는 인증 핸들러 런타임 확인을 끝냈다. 로그아웃 세션도 폐기된다. Cloudflare 원격 D1에 테스트 행을 넣는 추가 검증은 권한 오류 해소 후 재실행한다.
- [x] 정상 관리 API가 요청마다 GitHub `/user`를 재호출하지 않는다. `/user` 조회는 OAuth 콜백에만 있다.

**완료 조건:** 브라우저에 GitHub 토큰이 없고 본인 서버 세션만 관리 API를 사용한다. 로그아웃한 세션과 이전 인증 경로는 거절된다. 로그인·발행·업로드가 정상 동작한다.

**검증 기록 — 2026-09-28:** 스테이징에서 본인 OAuth 로그인 후 임시 글 발행, 합성 PNG 업로드와 이미지가 포함된 글의 공개 렌더링을 확인했다. 테스트 글은 스테이징 휴지통으로 이동했고 공개 글 주소는 404가 됐다. 업로드 이미지 객체는 스테이징 R2에서 200으로 응답한다. 7일 정책을 지키기 위해 수동 영구 삭제하지 않았다. 로그아웃 직후 스테이징 `/api/auth/session`은 401, `/admin/`은 로그인으로 302 이동했다. 비로그인 관리 API와 임의 Bearer만 보낸 관리 API는 각각 401이었다. 프로덕션 비로그인 `/api/auth/session`은 401, `/write/`는 로그인으로 302 이동했다. 스테이징은 `STAGE_EDITOR_PREVIEW` 설정 때문에 비로그인 `/write/` 요청에 HTML을 200으로 반환하지만, 편집기 클라이언트는 인증 확인 뒤 로그인 화면으로 이동하며 관리 API는 세션 없이는 401을 반환한다. 합성 세션 행을 사용해 배포된 CMS의 세션 핸들러를 메모리 D1 바인딩으로 실행한 결과 허용 계정 204, 다른 계정 401, 만료 세션 401, 비로그인 401을 확인했다. Cloudflare 원격 D1에 같은 테스트 행을 넣는 검증은 Wrangler의 현재 자격 증명이 D1 접근을 거부해 수행하지 못했다(Cloudflare API 오류 7403). 해당 행은 삽입되지 않았다.

### A3. 콘텐츠 기준 통일과 변경 결과 보장

근거: 확인된 시리즈 목록 누락, 보안 S03/S07, 성능의 불필요한 정적 산출물. 현재 삭제 글 노출 사례를 발견한 것은 아니다.

#### A3.1. 시리즈 전체 글 목록과 페이지네이션 복원 — 완료

- [x] D1 글 상세 페이지에 기존 시리즈 전체 글 목록을 복원한다. 기존 디자인 자산과 `SeriesPostPagination`의 동작을 우선 재사용한다.

**A3 완료 조건:** 시리즈 목록을 포함한 운영 콘텐츠가 D1 기준으로 조회된다. 사이트가 제공하는 다른 경로에서 삭제한 글이나 수정 전 원문이 다시 나오지 않는다. 재시도로 중복 글이나 조용한 덮어쓰기가 생기지 않는다. 외부 검색엔진·복사본 회수는 보장 범위가 아니다.

### A4. 배포 검증·실패 대응 고정

근거: 이번 대화에서 정한 안정화 완료 기준. 기존 배포·검증 수단을 먼저 확인하고 부족한 항목만 보완한다.

#### A4.1. 남은 보안 방어 보완

- [x] 관리자/로그인에 프레임 제한과 CSP를 적용한다. Astro 인라인 코드·OAuth·미리보기·이미지 업로드와의 호환을 확인한다. (S05)
- [x] 요청 전체 크기 상한을 전체 버퍼링 전에 적용한다. 잘못된 JSON·이미지와 Content-Length가 없는 요청도 다룬다. (S08)
- [x] 취약한 커밋 도구 의존성을 상위 도구 업데이트 또는 미사용 도구 제거로 해결한다. 실행 시 의존성 감사 결과를 다시 확인하고 호환성 없는 강제 override는 피한다. (S09)

**A4.1 완료 — 2026-09-30:** `worker/site.mjs`의 공통 관리 HTML 응답에 `frame-ancestors 'none'`, `X-Frame-Options: DENY`, CSP를 적용했다. `wrangler.jsonc`에 로그인 경로를 Worker 우선 대상으로 추가했다. Workers의 HTMLRewriter가 응답마다 만든 nonce를 Astro 스크립트에 붙이며 인라인 이벤트·eval·object·base 삽입을 차단한다. React·미리보기의 스타일 호환을 위해 `style-src 'unsafe-inline'`은 유지하고, 본문 이미지의 HTTPS/data/blob는 허용한다. 공개 페이지 전체 CSP 적용이나 전체 보안 감사는 이번 범위가 아니다. 정책 근거는 [Cloudflare HTMLRewriter](https://developers.cloudflare.com/workers/runtime-apis/html-rewriter/), [MDN script-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src), [MDN frame-ancestors](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors)다.

**요청 제한:** 저장·발행·삭제·복원 JSON과 이미지 업로드가 같은 제한 읽기 함수를 사용한다. 요청 전체 상한은 10MiB(10,485,760 bytes), 기존 Markdown 상한 1,500,000 bytes는 유지한다. JSON escaping 여유와 기존 10MiB 이미지 상한을 보존했다. Content-Length 초과는 읽기 전 413, 길이 없음·과소 신고는 실제 수신 바이트가 상한을 넘는 즉시 읽기를 취소하고 413을 반환한다. 잘못된 길이·UTF-8·JSON·JSON 객체가 아닌 값·이미지 서명·읽기 실패는 400으로 거절한다. 제한 이내 본문은 파싱/기존 이미지 검사에 필요한 만큼 버퍼링하며, 플랫폼이 한 번에 전달하는 chunk 자체의 할당까지 제어하는 것은 아니다. 기존 이미지 검사 수준을 유지했으며 이미지 전체 디코딩 검증을 새로 추가하지 않았다.

**커밋 도구:** `pnpm audit --json`에서 S09의 `tmp@0.0.33` 두 공지를 재확인했다. npm 조회 결과 최신 commitizen/cz-customizable도 문제가 되는 경로를 유지해, CI·Husky에서 쓰지 않는 프롬프트 도구와 `.cz-config.cjs`를 제거했다. `pnpm commit`은 기본 `git commit`을 실행하며 commitlint 훅은 유지한다. 강제 override와 새 의존성은 없다. 제거 후 감사에서 해당 tmp 경로는 사라졌다. 전체 감사는 low 3·moderate 8·high 6이며 undici(cheerio), fast-uri(Astro 검사), brace-expansion(ESLint 계열) 공지가 남아 있다. 감사 전체가 통과했다고 주장하지 않으며 이들은 이번 커밋 도구 정리와 구분한 후속 점검 대상이다.

**검증:** `pnpm verify:security`를 빌드 후 CI에 연결했다. CMS의 실제 핸들러로 크기 사전 거절·길이 없는/과소 신고 스트림의 즉시 중단·정확한 10MiB 경계·잘못된 JSON/이미지·거절 요청의 R2 미기록을 확인한다. Wrangler에 이미 설치된 Miniflare의 실제 Workers 런타임으로 빌드된 로그인/관리/편집 HTML과 index.html 경로의 nonce·CSP·프레임 헤더, 응답마다 nonce 변경, 비로그인 이동을 검증한다. Astro 검사 오류 0·경고 0(기존 hint 5), 빌드, 콘텐츠 일관성·검색·D1 경로·시리즈 회귀 검사를 통과했다. 새 검사 파일의 ESLint와 Worker 문법 검사를 통과했다. Worker 파일 기본 ESLint는 기존 전역 API 설정 누락과 기존 정규식 escape 때문에 실패하므로 전체 lint 통과로 기록하지 않는다.

**스테이징:** CMS `472fbffa-f8cf-4a12-9fa7-bade7fe5016a`(읽기 실패 처리 보완 후 `0dc7f0d4-f5db-4648-b41f-4bb986b60e91`), 사이트 `32f4a296-a116-45a5-b0ce-bf52aa308aca`로 배포했다. Chrome에서 본인 GitHub OAuth 로그인→편집기 초기화, Markdown 미리보기, 합성 1px PNG 업로드·미리보기 로딩(`naturalWidth=1`), 관리자 목록 초기화를 확인했고 조회한 브라우저 error/warn 로그는 없었다. 별도 로컬 HTML에서 스테이징 로그인 페이지를 iframe으로 불러오면 브라우저가 표시를 거절하는 것도 확인했다. 검증 글은 저장·발행하지 않았고 운영 데이터로 변경 실험을 하지 않았다. 스테이징 업로드 `posts/6877c20f-025c-4a20-bb08-f5841c3f4207.png`는 기존 7일 미사용 이미지 정리 정책에 맡긴다. OAuth 팝업 경로는 A2에서 제거된 상태이며 현재 페이지 이동 흐름을 검증했다. 초과 요청의 스트림 중단은 격리 런타임 검사이며 운영 부하 실험을 하지 않았다.

**운영 반영:** [PR #28](https://github.com/whateveriiwant/devlog/pull/28)의 [PR CI](https://github.com/whateveriiwant/devlog/actions/runs/36702321560)가 통과했고 `ab587d8`로 main에 머지했다. [프로덕션 자동 배포](https://github.com/whateveriiwant/devlog/actions/runs/36702537864)의 CMS·사이트 배포 단계가 모두 성공했다. Wrangler 배포 조회에서 CMS `f451a0cd-45e8-4b80-914e-1b1c8b18e48f`와 사이트 `16f9fc88-98cb-4a8b-8d53-27defa21dd9f`를 각각 100% 배포로 확인했다. 운영 `/login/`의 CSP·DENY·HTML 스크립트 nonce 일치, `/login/index.html`의 같은 헤더와 307, 비로그인 관리자·편집기 302 및 세션 401, 공개 목록·검색·상세 200, 폐기된 검색 원문 404를 확인했다. Chrome에서 본인 OAuth 로그인 후 관리자와 편집기 초기화 및 조회한 error/warn 로그 없음도 확인했다. 운영 글 저장·발행·삭제·이미지 업로드는 하지 않았다.

**복구·한계:** DB 스키마/이미지 주소 변경은 없다. 문제가 생기면 호환되는 사이트/CMS 코드를 수정 배포하거나 이전 코드로 복구할 수 있지만, A4.1 방어가 빠지는 완전 롤백은 해당 보호를 제거한다. 실제 이전 버전 롤백 훈련은 다음 A4.2에 남겨 둔다.

#### A4.2. 배포 검증과 복구 절차 고정

- [ ] 핵심 검증을 고정한다: 권한 거절, 세션 폐기, 초안, 발행·수정, 삭제·복원, 업로드·이미지 참조, 중복 요청·revision 충돌, 상세 페이지 시리즈 목록·페이지 이동.
- [ ] 대량 목록·잘못된 입력·응답 유실 등 영향이 큰 실패 조건을 별도 환경에서 확인한다. 운영 글을 검증 데이터로 사용하지 않는다.
- [ ] 필수 검증을 CI와 배포 절차에 연결한다. 빌드 통과만을 제품 동작 확인으로 취급하지 않는다.
- [ ] 실패 상태를 사용자에게 표시하고, 관리 API·DB 오류 시 예전 콘텐츠를 성공 응답처럼 제공하지 않는다.
- [ ] 기존 Cloudflare/Actions 로그에서 배포 버전, 오류와 필수 상태를 확인하는 최소 절차를 만든다. 토큰·본문·초안은 로그에서 제외한다.
- [ ] 사이트/CMS Worker의 호환되는 이전 버전, 배포 순서, DB 변경의 복구 전략을 문서화한다. 코드 롤백만으로 DB가 되돌아간다고 가정하지 않는다.
- [ ] 별도 환경에서 이전 버전으로 되돌리고 콘텐츠 조회·관리가 가능한지 확인한다.

**완료 조건:** 핵심 검증을 같은 절차로 재실행할 수 있고, 배포 실패의 확인·코드 복구·데이터 복구 경로가 기록되어 있다. A1–A3 결과와 함께 근거를 남긴다.

### 첫 안정화 종료 기준

- [ ] 본인만 관리 기능에 접근하고 로그아웃하면 기존 세션도 무효화된다.
- [ ] 발행·수정 실패를 성공으로 표시하지 않으며 재시도가 중복 글을 만들지 않는다.
- [ ] 삭제 결과가 서비스의 목록·검색·상세에 일관되게 반영된다.
- [ ] 운영 백업으로 글과 필요한 이미지를 복구할 수 있다. 복구 기간·한계가 명확하다.
- [ ] 문제가 생긴 배포를 호환되는 이전 버전으로 되돌릴 수 있다.

이 다섯 조건과 A3.1의 기존 기능 복원이 충족되면 첫 안정화를 종료한다. 전체 보안 감사 완료나 무장애 보증을 의미하지 않는다. 이 목록은 안정화 전체 종료 때 확인하는 종합 기준이며 A1/A2의 개별 완료를 취소하지 않는다.

## B. 안정화 다음에 실행할 성능·비용 작업

### B1. 실제 사용량 측정과 공개 API 보호

- [ ] Cloudflare/GitHub의 실제 플랜·청구·사용량을 확인한다. 현재 DB 크기와 성장률, R2 용량, CPU, 요청, rows_read/rows_written, Actions 분을 기록한다.
- [ ] 편집 진입·입력·검색·이미지 로딩의 현재 값을 측정한다. 과거 이미지 지연 원인을 코드만으로 확정하지 않는다.
- [ ] 기존 WAF/호출 제한 설정을 확인한 뒤 고비용 공개 검색·태그 API에 최소 호출 제한을 적용한다. 정상 이용과 제한 초과 응답을 확인한다. (S06)
- [ ] 한도·오류 대응 절차를 정한다. 무료 한도 장애와 유료 초과 과금을 구분하고, 예산 알림을 비용 상한으로 취급하지 않는다.

**완료 조건:** 측정 기준값과 현재 운영 여유가 기록되고, 고비용 API의 반복 호출을 제한할 수 있다. 공개 API 악용이나 한도 임박이 확인되면 이 작업을 앞당긴다.

### B2. 관리 목록과 편집기

- [ ] 관리 목록에 서버 페이지네이션·검색·필터·전체 집계를 적용한다. 상태별 500개 제한 때문에 글이 누락되지 않게 한다.
- [ ] 500개를 넘는 별도 데이터에서 마지막 글의 조회·검색과 개수를 확인한다.
- [ ] 글 열기에서 전체 발행·초안·휴지통 조회를 제거하고 선택 글과 필요한 시리즈만 먼저 읽는다.
- [ ] 미리보기 OFF에서는 Markdown 변환을 실행하지 않는다. ON에서는 짧은 debounce와 정제를 유지한다.

**완료 조건:** 글 수가 많아져도 관리할 수 있고 한 페이지 규모만 전송한다. 편집 진입과 입력에 불필요한 전체 작업이 없다. 실제 목록 누락이 발생하면 B2를 안정화 작업으로 앞당긴다.

### B3. 공개 조회·검색·태그

- [ ] 공개 데이터/HTML 캐시와 변경 시 무효화를 함께 적용한다. 초안·관리 응답·인증 정보는 공개 캐시에 넣지 않는다.
- [ ] Cache API의 지역별 동작을 고려해 전역 변경 반영을 확인한다. TTL 증가만으로 즉시 반영을 약속하지 않는다.
- [ ] 검색 더 보기에서 받은 결과를 재사용한다.
- [ ] 태그 관계 집계를 화면에 필요한 범위로 제한하고 재사용한다.
- [ ] 실제 검색 rows_read와 한글 검색 품질을 보고 FTS5 도입 여부를 결정한다.

**완료 조건:** 반복 공개 조회의 DB 읽기·CPU가 줄고, 발행·수정·삭제·복원이 캐시 때문에 지연되거나 유출되지 않는다.

### B4. 이미지·CI·정리 작업

#### B4.1. 이미지 전달 개선

- [ ] D1 본문 이미지의 lazy loading/async decoding을 통일한다. 화면 첫 주요 이미지의 표시를 늦추지 않게 적용한다.
- [ ] 업로드 시 작은 썸네일을 생성·재사용하는 방식을 검토한다. 기존 JPEG/PNG 축소·더 작은 WebP 선택을 유지한다.
- [ ] R2 custom domain의 실제 CDN 캐시 적중을 확인한다. R2 Standard와 새 URL 방식의 긴 캐시를 유지한다.

#### B4.2. 필요한 CI/CD만 실행

- [ ] 문서만 변경하면 배포를 생략하고 Worker 변경에는 필요한 빌드·배포만 수행한다. 기존 의존성 캐시를 재사용한다.

#### B4.3. 이미지 정리 작업 비용 절감

- [ ] 이미지 정리의 D1 확인을 제한된 묶음으로 처리하고 불필요한 설치·이력 조회를 줄인다. Git 참조 검사는 A3 이전 완료 후에만 제거를 검토한다.
- [ ] 이미지 정리의 7일 유예·최신 참조 확인·실패 중단을 다시 확인한다. `posts/` 전체에 생성 후 7일 삭제 lifecycle을 적용하지 않는다.

**완료 조건:** 이미지 전송과 CI/정리 비용이 줄고 정상 발행·사용 중 이미지 보존에 회귀가 없다.

## C. 운영 선택과 장기 관리

- [ ] A2/A3 후 저장소 private 전환 여부를 결정한다. 포트폴리오 공개 목적, Actions 포함 분·저장량과 외부 연결 영향을 확인한다. private 전환을 웹 보안 해결책으로 취급하지 않는다.
- [ ] 무료 플랜을 유지할지 실제 CPU·DB·사용량으로 결정한다. 필요할 때 최소 유료 플랜을 검토하며 기본료를 총액 상한으로 약속하지 않는다.
- [ ] 월 1회 사용량·청구·백업 성공 여부를 확인하는 절차를 기록한다. 이 문서만으로 예약 자동화는 생성하지 않는다.
- [ ] 분기별 복구 확인, 계정 복구 수단, 도메인 갱신·만료 확인 절차를 정한다.
- [ ] DB 약 350MB, R2 약 8GB, 무료 사용량 약 70%를 사전 점검 기준으로 검토한다. 공급자 한도가 아닌 제안값이다.
- [ ] DB 증가량을 실제로 기록한다. 본문을 R2로 분리하거나 다른 DB로 이전하는 작업은 용량·운영 필요가 확인되기 전에는 추가하지 않는다.

## 진행 기록 규칙

각 항목을 완료할 때 변경 파일/배포 버전, 수행한 검증과 결과, 복구 방법, 남은 한계를 기록한다. 구현만 끝났거나 별도 환경만 통과했다면 운영 완료로 표시하지 않는다.

새 발견이 실제 데이터 손실·권한 우회·운영 장애에 해당하면 우선순위를 조정하고 이유를 기록한다. 단순 기능 추가와 추측성 최적화는 A1–A4의 완료 조건을 늘리지 않는다.
